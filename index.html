  2. スモウルビーを開く ↗。
  3. 左上の ファイル をクリック。

緑の旗を押すと、自分の機体は最初から← →で動きます。通信前は相手に反映されず、弾も出ません。5か所の入力を完成させて、順に確かめます。

この版はメッシュの更新間隔を短くするものではありません。遅れて届いても発射情報を保持し、届いたかを確認する学習用の仕組みです。

STEP 1 / 接続

ペアだけのグループをつくる。

  1. メッシュの接続画面が出たら、その画面を使う。出なければ、左下の拡張機能から メッシュ を選ぶ。追加済みなら接続ボタンを押す。
  2. 教員の指定した ドメイン を2人とも同じにする。別ペアと混ざらないよう、日付・ペア番号・ランダムな文字を含める。
  3. A側は メッシュのホストになる（グループの作成） を選ぶ。
  4. B側は メッシュに参加する（グループに参加） から、Aのホスト名を選ぶ。
  5. 読み込み直した場合は接続状態を確認し、必要なら同じグループへ入り直す。

学校全体で1つのグループに入らず、1ペアにつき1グループ、A・Bを1つずつにします。テスト用に余分に開いた作品も接続しません。

✓ 接続操作が終わっても、まだ「返事待ち」でOK。次で受信のプログラムを入れます。

PLAY / 動かして確かめる

接続 → 準備 → 対戦。

  1. 2人とも停止ボタン→緑の旗。
  2. 双方の画面に 接続OK が出るまで待つ。
  3. ステージを一度クリック。キーボードを半角英数にし、2人とも G を押す。
  4. ← → でレーンを変える。スペース で発射。
  5. 発射直後は「返事待ち」。受信確認が来るまで次の弾は出ない。
  6. 相手からのビームに当たると、自分のライフが1減る。ライフ0で終了。

ヒント
数字は半角。-140、0.05、1 と入力します。
「ー１４０」「０．０５」は使いません。

自分の画面の発射表示と、相手が受け取ってから始まるビームには時間差があります。当たり判定は、受信した側で自分の機体に対して行います。

✓ ①双方が接続OK ②両方向にレーンが届く ③発射番号が増える ④相手の受信番号に反映 ⑤同じ弾が重複しない ⑥ライフが減る

HELP / 返事を見ながら直す

止まった場所が、見える。

表示・症状確かめるところ
返事待ちのまま同じグループ？ AとBを1つずつ？ STEP 2の起動ID・返事が逆ではない？
自分だけ動き、相手に出ないSTEP 3の相手レーン。Aで青を動かすとBの青が動きます。
接続OKだが弾が出ない双方がGを押した？ まだ準備・発射確認待ち？ ステージにキーボードの操作が入っている？
1発目のあと返事待ちが続くSTEP 4の発射番号・受信番号。ペアの反対側も同じ2か所を確認。
通信中断約8秒、相手の時計の更新が届かなかったか、相手が起動し直しました。接続を確認し、両方停止→旗→接続OK→G。
勝敗がずれて見えるライフも通信で届くため遅れます。相手の画面が更新されるまで待つ。

数値が同じでも、相手が動作中かを確かめるため、時計の番号を送っています。通信中断時は対戦を止めます。発射の返事が遅くても、勝手に次弾を送ったり、同じ弾を増やしたりしません。

メッシュの通信速度自体や学校の通信制限は、このプログラムでは変更できません。長い停止が続く場合は、管理担当者に graphql.api.smalruby.app へのHTTPS・WebSocket（443）を確認してもらいます。

REFERENCE / 完成見本

5か所の差だけで、完成。

Aの完成見本 ↓Bの完成見本 ↓

スターターと完成見本の違いは、ガイドで入れる センサーブロック5個だけ。送受信の管理、時計、ビーム、ライフのプログラムは共通です。

先頭の「緑の旗が押されたとき」「クローンされたとき」は帽子形です。上にブロックをつなげません。この教材では、下にある数値の入力欄へセンサーを入れます。

時間の目安内容
0〜10分読み込み・接続・自分のレーン操作
10〜20分IDと返事を受信して接続OKを確認
20〜30分レーンの送受信
30〜40分発射番号と受信確認、対戦
40〜50分送る情報・返す情報・遅れへの工夫を説明

振り返りの問い

何を送った？ 相手は何を返した？ なぜ返事を待つ？ 更新が届かない間、どの情報を残しておくとよい？

起動IDは毎回変わる確認用の番号で、ログインや本人確認ではありません。ドメインやグループ名にも本名を使いません。

検証範囲：通信を模した遅延・欠落・重複・切断テストとファイル構造を確認済みです。学校回線・実際のメッシュでの接続は、授業前にこの完成見本を2台で試してください。
